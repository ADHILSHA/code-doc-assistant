## Phase 5

**Private-repo auth: PAT, not GitHub OAuth device flow — user's explicit choice**
SPEC.md §6 Phase 5 task 2 offers either. OAuth requires registering a GitHub OAuth App (client id/secret) with GitHub first — an external, one-time setup step the implementing agent cannot do on the user's behalf. Presented as a real fork via `AskUserQuestion`; the user picked PAT. A pasted PAT is stored encrypted at rest (Fernet, `app/security/credentials.py`, key from `CREDENTIAL_ENCRYPTION_KEY`), used only as a git credential, never logged or returned by the API (`GET /api/auth/github-token` reports only `{configured: bool}`).

**A stored PAT is passed to `git clone`/`git fetch` as a per-invocation `-c http.extraheader=...` override, not embedded in the clone URL**
The obvious approach — `https://x-access-token:{token}@github.com/owner/repo.git` — gets written verbatim into the new clone's `.git/config` (`remote.origin.url`) by `git clone` itself, leaving the token sitting in plaintext on disk for as long as the clone exists, and resurfacing in `git remote get-url origin` (used by the incremental-reindex fetch/reset path to verify it's refreshing the right clone). A `-c` config flag only affects the single git process it's passed to and is never persisted — verified by actually cloning against a local `file://` remote with a fake token and grepping the resulting `.git/config` for it (`tests/test_source.py`). Git stderr is also defensively scrubbed of the raw token before it can reach a `SourceError` message, in case a future error path routes token-bearing text through git's own output.

**Secret redaction (`app/ingest/redact.py`): real bug found via smoke test, not inspection — the original high-entropy scan missed secrets inside triple-quoted docstrings**
First implementation only scanned inside `"..."`/`'...'`/`` `...` `` quote-delimited spans for high-entropy candidates. A `"""..."""` docstring opens with three consecutive `"` characters, so a single-quote-anchored regex's capture group matched an essentially-empty span right at the start of the triple-quote and never reached the actual docstring text — found by indexing a fixture with a fake secret inside a docstring and checking the stored `symbols.docstring` column, not by reading the regex. Fixed by scanning raw token-shaped runs (`[A-Za-z0-9+/=_.\-]{20,}`) directly over the whole text instead of only inside quote spans, which also still catches every quoted-literal case the old regex covered. Regression-tested explicitly (`tests/test_redact_integration.py::test_docstring_secret_is_redacted_in_symbols_table`).

**Redaction happens at the DB-storage boundary (`index/store.py`, `index/graph_store.py`), not at every downstream read site — except the agent's `read_file`/`grep` tools, which need their own explicit calls**
Storing already-redacted content in `chunks`/`symbols` is provably complete for the embedding + hybrid-search + agent's `semantic_search` + synthesis-context path, since all of those read *from* those tables, never from raw file text again. But `read_file`/`grep` (`app/agent/tools.py`) bypass the DB entirely — they read live from disk via `safe_join`, the same as the repo's own working tree — so they're a distinct path requiring their own redaction calls. Reasoned through and implemented before testing, not discovered as a gap afterward; verified with dedicated tests forcing both the ripgrep and pure-Python grep fallback paths.

**Request-timeout middleware is a raw ASGI class (`__call__(scope, receive, send)`), not a `starlette.middleware.base.BaseHTTPMiddleware` subclass — found necessary by testing, not chosen upfront**
First version wrapped `asyncio.wait_for` around `call_next(request)` inside `BaseHTTPMiddleware.dispatch`. That correctly produced a 504 response object on timeout, but timing a real request against it showed the *client* still waited for the full, un-cancelled handler duration (a 3s dummy handler against a 1s timeout delivered its 504 at ~3s, not ~1s). Cause: `BaseHTTPMiddleware.call_next()` doesn't run the downstream app inline — it spawns it as a sibling task in an internal task group and relays messages through an in-memory stream; cancelling the coroutine *my* dispatch was awaiting only cancelled that relay, not the sibling task, and the task group's exit still blocked on the sibling finishing. Rewriting as a raw ASGI middleware — `asyncio.wait_for(self.app(scope, receive, send_wrapper), timeout=...)` called directly, no task-group indirection — fixed it: re-measured, a 0.5s handler against a 0.1s timeout now delivers the 504 at ~0.1s, and the handler's own `await asyncio.sleep(...)` is genuinely cancelled (confirmed the handler's post-sleep code never ran), not merely orphaned to finish in the background. Two honestly-documented residual limits, not silently glossed over: (1) this can't forcibly kill a *synchronous* route handler already running on an OS thread (FastAPI's threadpool) — Python can't do that; (2) for the one streaming endpoint (`/api/query`, SSE), the timeout only bounds time-to-first-byte, not total stream duration (already independently bounded by the agent loop's own `agent_max_wall_seconds`).

**Middleware resolves `Settings` per-request via `request.app.dependency_overrides`, not once at `create_app()`-time — real bug found via smoke test**
`main.py::create_app()` calls the real, process-wide `@lru_cache`'d `get_settings()` directly (not through FastAPI's `Depends()` machinery) to configure CORS — an existing pattern this session's rate-limit/timeout middleware initially copied by taking `settings` as a constructor argument. That silently broke every test expecting a per-test `Settings` override: `app.dependency_overrides[get_settings]`, set *after* `create_app()` returns, never reaches something already baked in at construction time. Found when a rate limit of 3 configured through `make_settings(...)` never tripped across 6 rapid test requests. Fixed by having both middlewares resolve `Settings` fresh on every request via `request.app.dependency_overrides.get(get_settings, get_settings)()` — the same override every route handler's `Depends(get_settings)` would honor, without needing to change `create_app()`'s signature or touch the existing test-setup convention used throughout the rest of the test suite.

**Raw provider exceptions are mapped to a short, actionable message before reaching the SSE `error` event — real bug found via a live smoke test against a real (temporarily out-of-credit) Anthropic account**
The unhandled exception's `str()` — `"Error code: 400 - {'type': 'error', 'error': {...}, 'request_id': '...'}"` — rendered verbatim in the chat UI's error state. `generation/answer.py::_user_facing_error_message` duck-types on `anthropic` SDK exception class names (module/type name, not an import-time dependency — same lazy-optional-dependency spirit as `providers/llm.py`) to produce a short, actionable message (auth, rate-limit, no-credit, connection, server-error, or a generic fallback) while the real exception is still logged in full server-side via the new structured logger, tagged with the request's `request_id`.

**Docker image installs `.[embeddings]`, not bare `.` — real bug found by actually running `docker compose up` and indexing a repo**
`pyproject.toml` splits `voyageai`/`openai` into an optional extra (so the zero-network test suite's `FakeEmbeddingProvider` path doesn't need them). The backend Dockerfile's first pass installed only the base package, which built and started cleanly — then failed every index job with `ModuleNotFoundError: No module named 'openai'`, silently, since a missing embedding provider only surfaces once a real index is attempted. Never would have been caught by `docker build` succeeding alone; found by driving the running container with a real `POST /api/repos` call and reading the job's `error` field.

**Structured logging (`app/logging_setup.py`) uses a `contextvars.ContextVar`-backed `request_id`, populated by middleware, read by a `logging.Filter` — not passed as an explicit parameter through every function**
SPEC.md §6 Phase 5 task 4 asks for "structured logging with a `query_id` trace." A contextvar means any `logger.info(...)` call anywhere in the code during a request's handling automatically carries the same `request_id`, without threading it through every function signature down the call stack (retrieval, the agent loop, citation verification, ...) — the standard pattern for this in async Python web frameworks. Deliberately distinct from the *existing*, frozen SSE `done` event's `query_id` field (the `query_log` row's DB id, assigned only once an answer completes) — this is a per-*HTTP-request* trace id assigned at the very start of the request, before that row exists; a background indexing job (kicked off via `BackgroundTasks`, running after its originating request already returned — see `api/repos.py`) has no single request that "owns" it, so its log lines simply carry `request_id: null`, which is correct rather than a bug to paper over.

**Frontend ships one theme (dark) rather than a light/dark toggle — scope call, not an oversight**
SPEC.md §6 Phase 5 task 1 lists "dark mode" among the frontend polish items. The app has been dark-only (hardcoded Tailwind `neutral-*` utility classes throughout every component, no `dark:` variants) since earlier phases — building a *toggle* now would mean either redefining Tailwind's built-in neutral palette per-theme (fragile) or retrofitting `dark:` variants onto every hardcoded class across ~10 components (a large, error-prone mechanical change disproportionate to the remaining Phase 5 scope: Docker, README, PAT UI, error-state polish, and the auth/redaction/hardening backend work). Logged here rather than silently skipped, per the working agreement's "if a spec item turns out impractical at the planned scope, say so."

**Frontend Phase 5 polish verified live, via Playwright driving the actual running dev servers (and, separately, the actual Docker Compose deployment) against real backend data — not just `tsc`/lint/production-build passing**
Consistent with this project's established "verify → write code → smoke-test against real fixtures → fix what's found → formalize" pattern (see the Phase 3 summarization-progress entry). Concretely exercised: indexing and querying `pallets/flask` (structured `dependencies`/`endpoints` routes need no LLM call and were used to verify real markdown rendering + citation chips + syntax-highlighted `CodeViewer` end-to-end without needing API credit); a real Anthropic account that happened to be temporarily out of credit, which is what surfaced the raw-error-message bug above; keyboard Escape closing `CodeViewer` and the PAT settings popover; the `/` shortcut focusing the chat input; repo-row hover reindex/delete buttons; and the full Docker Compose stack (build → up → index a real public repo through nginx's reverse proxy → a real SSE-streamed query through that same proxy). One finding from this pass worth noting even though it didn't require a code change: `react-syntax-highlighter`'s `PrismAsyncLight` (lazy per-language loading) made `npm run build` emit a separate chunk file for every Prism-supported language (~250 files) even though only ~19 are ever registered — switched to `PrismLight` (synchronous, since every used language is already statically imported and registered up front) purely to keep the production build's output sane; functionally identical either way.

**Railway deployability: both Dockerfiles read their listen port from `PORT` (not hardcoded); nginx reverse-proxies to the backend's public URL, not Railway's private inter-service networking — the latter was tried first and reverted after a real test disproved the assumption behind it**
Railway (like most container PaaS platforms) assigns a random port per deployment via a `PORT` env var and expects the process to bind to it; `backend/Dockerfile`'s `CMD` and `frontend/nginx.conf.template`'s `listen` directive both do, defaulting to their previous hardcoded values (8000 / 80) so `docker-compose.yml`'s behavior is unchanged. Verified — not just asserted — by overriding `PORT` on each image standalone (`docker run -e PORT=9091 ...`) and confirming the service actually starts listening on the overridden port.

Getting the frontend→backend connection right took a wrong turn worth recording. First attempt used Railway's private inter-service networking (`<service>.railway.internal`), which Railway's own docs say requires binding to `::` (IPv6) rather than `0.0.0.0` — so `backend/Dockerfile` was changed to `--host ::`, expecting Linux's usual dual-stack default (a `::`-bound socket also accepting IPv4) to make this transparent for `docker-compose.yml`'s IPv4 bridge network too. Tested directly against a real `python:3.12-slim` container (not assumed from general knowledge) — a plain FastAPI app bound to `::` inside that container was **not** reachable via IPv4 through Docker's own port mapping (`curl` to the mapped host port got a hard connection failure), disproving the dual-stack-by-default assumption for this specific image. Rather than debug OS-level socket option config (`IPV6_V6ONLY`) for a networking topology (Railway private networking) that can't be tested end-to-end without a live Railway account, reverted to `--host 0.0.0.0` (the original, already-verified-working default) and redesigned the frontend↔backend connection to not need private networking at all: `frontend/nginx.conf.template`'s `/api` reverse proxy target is a templated `BACKEND_INTERNAL_URL` env var — `http://backend:8000` for docker-compose (Docker's embedded DNS, unchanged from before), the backend's **public** HTTPS URL for Railway. Still an entirely server-side proxied call (the browser only ever talks to the frontend's origin), so this doesn't reintroduce CORS or lose the "no cross-origin request" property the private-networking approach was chasing — it just uses a connection path (public HTTPS) that's actually been verified to work, instead of one (private IPv6 networking + dual-stack binding) that couldn't be fully verified here and, on the one piece of it that *was* tested, didn't behave as commonly assumed.

Two smaller findings from the same pass, both fixed: (1) a literal, unresolvable hostname (`backend`) baked directly into a non-templated `nginx.conf` would make nginx fail at *startup* the moment it's deployed somewhere that hostname doesn't resolve (Railway) — fixed by moving the whole reverse-proxy target behind envsubst templating (`frontend/nginx.conf.template`, processed by the official nginx image's built-in `/etc/nginx/templates/` entrypoint at container start, not build time). (2) nginx doesn't send SNI on a proxied HTTPS upstream by default, which would break routing through a platform that virtual-hosts multiple services behind shared edge IPs via SNI (Railway does) — added `proxy_ssl_server_name on;` (a no-op for the plain-HTTP docker-compose case, so one config file serves both).

## Phase 4

**`POST /api/eval/run` takes `{repo_id, suite}` against an already-indexed repo; the CLI (`python -m app.eval.run_eval --repo <name>`) additionally indexes**
SPEC.md §5's contract is `{repo_id, suite}`, which only makes sense against a repo the caller already indexed via `POST /api/repos` — so `run_eval_against_repo` (what the API calls) never indexes anything itself; `suite` just picks which `eval/golden/{suite}.yaml` to score that repo against, independent of the repo's own source. `run_eval` (what the CLI calls) is a thin wrapper that additionally resolves `repo_name` to one of SPEC.md §8's recommended test repos, indexes it if there's no `ready` index yet (or `--reindex` is passed), times that, and then calls `run_eval_against_repo` — because a CLI meant for local/CI use ("just evaluate flask") shouldn't require a separate manual indexing step first the way the API reasonably can. Both funnel through the same scoring logic; nothing about metrics computation differs between them.

**`POST /api/eval/run` is synchronous, per SPEC.md's literal contract — even though a large golden set through `explain`-route questions can take minutes**
Unlike `POST /repos` (backgrounded, polled via job status), SPEC.md §5 specifies `POST /api/eval/run {repo_id, suite} → eval report` — a direct response, not a job to poll. Every `explain`/`overview`-fallback question is a full agent-loop round trip (Phase 3), so a 20-25 question golden set can genuinely take several minutes end to end; live-verified against a real Anthropic account (see below) that one `explain` question alone took ~48 seconds. A production deployment would likely want this backgrounded the same way indexing is, but that's a deviation from the frozen API contract this phase didn't make unilaterally — flagging it as a known follow-up rather than silently changing the contract.

**`eval_report_dir` is a real overridable `Settings` field; `golden_dir` is not (both were originally one `eval_dir` property)**
First pass derived `golden_dir`/`eval_report_dir` from a single `eval_dir` property, matching the `data_dir` -> `clones_dir`/`dbs_dir` pattern already used elsewhere. That's wrong for eval specifically: `golden_dir` should always point at the real, committed question sets (a test run needs to exercise the actual authored golden set, not a copy), while `eval_report_dir` needs to be redirectable to a throwaway location in tests — writing real report files into the repo on every test run would be its own kind of test pollution, and unlike `data/clones`/`data/dbs`, `eval/report/*` is coupled to `eval_report_dir` specifically rather than a single shared root. Split into two independent `Settings` fields instead, each with its own real default, so tests override only the one that needs it (`make_settings(tmp_path, eval_report_dir=...)`).

**Incremental reindex's file-removal cleanup nulls cross-file references instead of deleting the referencing rows**
SPEC.md §6 Phase 4 task 4 says "delete orphaned chunks, symbols, refs, and vectors" for files removed from a repo. Read literally that could mean deleting a `symbol_refs`/`import_edges` row the moment its *target* file is gone — but the row's own *source* file/symbol is still real code that still makes that call/import; only the resolution target disappeared. `ingest/incremental.py::remove_stale_files` deletes rows the removed file *owns* (its own chunks, symbols, endpoints, outgoing refs) but only nulls `resolved_symbol_id`/`to_file_id` on rows *elsewhere* that pointed at it — same "an unresolved reference is honestly unresolved, not fabricated or erased" spirit as an invalid citation being stripped rather than the whole claim being deleted (generation/citations.py, Phase 1).

**Efficient reindex (`git fetch` + `reset --hard` instead of a full re-clone) is generic over the git URL, verified against a local `file://` remote in tests, not github.com**
SPEC.md §7.2 forbids network calls in tests. `ingest/source.py::_try_fetch_and_reset` doesn't know or care that production URLs happen to be `https://github.com/...` — `git fetch`/`git reset --hard`/`git clean` behave identically regardless of transport, so `tests/test_source.py` builds a real local bare repo (`git init --bare`) and clones/fetches against its `file://` URL, exercising the actual git subprocess mechanics (not a mocked one) while making zero network calls. `_clone_github`'s own branching logic (try fetch+reset first when `dest` already looks like a matching clone, fall back to a fresh clone on any failure) is covered separately with a mocked `subprocess.run`, matching the existing test's style for that function.

**Real finding, from an actual paid eval run against pallets/flask, not a synthetic test: one golden question's wording accidentally triggered the wrong router fast-path**
`eval/golden/flask.yaml`'s `flask-explain-002` originally asked "How does Flask's add_url_rule method register a new **route**?" — an `explain`-shaped question that happens to contain the literal word "route", which `retrieval/router.py`'s endpoints fast-path regex (`\b(endpoints?|routes?|...)\b`) reads as an unambiguous endpoints-question signal, per its documented precedence (checked before the broader `explain` patterns — see the Phase 2 entry below on why). The router did exactly what it's supposed to do given that wording; the bug was in the golden question's own phrasing implying a different intent than what its literal words say. Reworded to "...wire up a new URL **rule**?" (matching the real `add_url_rule` API's own terminology) to remove the ambiguity, and left a `notes:` line on the entry explaining why, so a future contributor doesn't "fix" it back. Also surfaced, same run: the account's Anthropic credit balance ran out partway through a ~20-question golden set — each affected question failed independently with a clean, captured error (`QuestionResult.error`), the eval harness kept going and still produced a complete report with the successful questions' real numbers (citation_validity 1.0 across every question that got a real answer; the one `explain` question that completed before credits ran out scored a perfect correctness=2), rather than crashing the whole run — real evidence the same graceful-degradation contract that's been enforced throughout this project (a keyless/failed LLM call surfaces cleanly, never crashes the caller) holds under a genuine real-world failure it wasn't specifically written to anticipate.

## Phase 3

**Real bug, found from a live user report: indexing jobs on larger repos sat at "summarizing" (90% progress) for a long time with zero visible movement — looked hung, wasn't**
`jobs.py` originally summarized every uncached file strictly one at a time (`enrich/summarizer.py::summarize_repo`'s file-level loop), each requiring its own LLM round-trip, and only set the job's `progress`/`message` *once* before the whole stage — for a repo with dozens of summarizable files, that's dozens of sequential API calls behind one static "Generating hierarchical summaries" message, easily (and reasonably) mistaken for a hang even though it was still working. Fixed two ways:
1. File-level summaries are independent of each other (unlike directory/repo-level ones, which need their children's summaries first already-computed) — `summarize_repo` now takes a `concurrency` parameter and runs that many summarization calls at once via a `ThreadPoolExecutor`, default `Settings.summary_concurrency = 6`. Only the LLM call itself runs on worker threads; every DB read/write stays on the calling thread, since a single `sqlite3.Connection` isn't safe for concurrent multi-threaded use — content is fetched up front, and each worker result is written back sequentially as `pool.map` yields it. Verified with an artificially slowed `FakeLLMProvider`: 6-way concurrency measurably beats sequential timing in `test_summarize_repo_runs_file_level_calls_concurrently`.
2. `summarize_repo` takes an `on_progress(done, total)` callback, invoked after each file's summary is written; `jobs.py` wires this to real incremental `_update_job` calls (`"Summarizing files (12/48)"`), spread across the 0.90-0.98 progress range, instead of one message for the whole stage.

Also added `Settings.summary_max_files_per_run` (default 300, same cost-guardrail spirit as `MAX_CHUNKS_PER_REPO`): uncached files beyond the cap are simply left for a later reindex rather than summarized unboundedly in one run, bounding worst-case latency on very large repos. None of this changes correctness (caching by `source_hash` still works exactly as before, verified by the existing cache tests still passing unmodified) — purely a latency/visibility fix.

**`explain` always routes through the agent (retrieval -> expansion -> rerank -> tool loop) — no separate "is this complex enough for an agent" classifier**
SPEC.md's Phase 3 goal is "correctly answer multi-hop questions," but not every `explain`-routed question is multi-hop. Rather than add a second router layer to decide "simple flat-LLM-call" vs. "full agent," every `explain` question (and the `locate`/`overview` structured-route fallbacks) goes through the same agent path. This works because the agent's first turn can always answer directly with zero tool calls when the seeded context already suffices — verified live against a real model (`"Where is UserService defined?"`-style simple questions resolve in one LLM turn, no tools called), so simple questions aren't meaningfully more expensive than the old flat path, while multi-hop questions get real tool-use investigation. Avoids a second classifier with its own accuracy/cost tradeoffs for a distinction the agent's own behavior already makes moot.

**Agent path does not retry-once on an unsupported citation, unlike the Phase 1-2 flat LLM path**
`_answer_via_hybrid_retrieval`'s (now `_answer_via_agent`'s) predecessor called the LLM a second time with `REGENERATION_NOTE` if `verify_citations` found a claim with no valid citation. Re-running that logic for the agent path would mean re-running a whole multi-turn tool-use loop (many LLM calls, real added latency/cost) for one retry — judged not worth it. `verify_citations` still strips any invalid citation from what's shown (so nothing hallucinated ever reaches the user), just without a second full attempt at getting every claim cited. If this turns out to matter in practice, the cheapest fix is probably a single non-agentic retry call (reusing the accumulated seed context, no new tool calls) rather than re-running the full loop — not implemented, flagging as a known gap.

**Only file-scoped summaries are embedded into `chunks`/`chunk_vectors`; directory/repo-scoped summaries live only in `summaries`**
SPEC.md §6 Phase 3 task 4 says "embed summaries into the same vector index with `symbol_kind='summary'`" without qualifying scope. `chunks.file_id` is `NOT NULL` (SPEC.md §4), and a directory- or repo-level summary has no single file to attach to. Rather than relax that constraint or invent a synthetic file row, only file-level summaries (which do have a real `file_id`) get embedded as searchable chunks; directory/repo summaries are read directly out of `summaries` by scope/target_path — which is also a better fit for the acceptance criterion "answers correctly using summaries *without reading source files*" than hoping semantic search reliably surfaces a repo-level summary among hundreds of code chunks.

**`query_log.session_id` column added via migration v4 — not in SPEC.md §4's schema**
"Rewrite follow-up questions against the last 3 turns" (Phase 3 task 5) needs a way to find "the last N turns of *this conversation*." `query_log` is already the per-repo turn history, so a plain `ALTER TABLE query_log ADD COLUMN session_id TEXT` (indexed) reuses it instead of introducing a parallel conversation-log table. The logged `question` is the *resolved* (pronoun-rewritten) text, not the raw user input — simplifies the threading (one `question` variable throughout `generate_answer_events` instead of separately tracking raw-vs-resolved) and arguably produces more stable multi-turn context, since a rewritten, self-contained question doesn't accumulate pronoun ambiguity across turns the way raw text would. The frontend's chat bubbles still show exactly what the user typed — they're rendered client-side from the input box, never round-tripped from `query_log`.

**`complete_with_tools`'s `messages` parameter is Anthropic-shaped, breaking from `complete()`/`stream()`'s vendor-neutral `{"role", "content": <str>}` dicts**
A multi-turn tool-use conversation needs structured message content (an assistant turn's `tool_use` blocks, a user turn's matching `tool_result` blocks) that a plain string can't represent. Rather than design a second, fully vendor-neutral message-content abstraction only for tool conversations, `agent/loop.py` builds Anthropic's native block shape directly, and `AnthropicLLMProvider.complete_with_tools` passes it straight through. `FakeLLMProvider.complete_with_tools` accepts the same shape but (like the rest of the fake) never touches an SDK type — it just returns scripted `ToolUseResponse`s. The *response* shape stays fully vendor-neutral (`ToolCall`/`ToolUseResponse` dataclasses — SPEC.md §7.2's "never call vendor SDKs directly from business logic" holds for everything `agent/loop.py` reads), only the request shape leaks the vendor's conversation format. Documented as a deliberate, scoped compromise for a single-provider (Anthropic) project, not an oversight.

**Reranking is LLM-based (cheap model), not a cross-encoder**
SPEC.md §6 Phase 3 task 2 offers "cross-encoder or LLM-based scoring" as alternatives. A cross-encoder means a new heavy model dependency (sentence-transformers + a downloaded model) purely for this one step — duplicating the provider-abstraction problem already solved for embeddings/LLMs, for a system that otherwise has zero local-model dependencies (see Phase 0's `fastembed` removal). `retrieval/rerank.py::rerank` reuses whatever `LLMProvider` it's given — `generation/answer.py` passes the cheap summarization-tier provider, the same one `retrieval/router.py`'s LLM fallback and `enrich/summarizer.py` use — and fails open (keeps the incoming order, truncated to `keep_n`) if the response can't be parsed into a valid ranking, so a reranking hiccup never breaks the whole answer.

**`run_agent` is a generator yielding live tool-call events, not a function returning a final result with a callback**
First implementation returned `AgentResult` and took an `on_tool_call` callback, mirroring a natural "run this, get a report back" shape. Caught before it was wired into `generation/answer.py`: SPEC.md §5 requires the SSE `tool` event to fire *live*, one per call, as the UI's reasoning trail — a callback invoked synchronously deep inside a plain function can't be interleaved with `generate_answer_events`'s own `yield`-based SSE event stream without extra machinery (a queue, a thread). Since every other part of the answer pipeline is already a plain sync generator yielding event dicts (the same pattern `api/query.py`'s `_to_async_iter` offloads to a thread per `next()` call), making `run_agent` a generator too — yielding `AgentToolEvent` per tool call and one final `AgentDone` — was the natural fit, not a workaround. Caught by re-reading SPEC.md §5's frozen event contract before wiring the loop into `answer.py`, not by a failing test.

**mini_repo fixture gained a real four-file call chain (`tests/test_service.py` -> `src/users/service.py` -> `src/auth/auth.py` -> `src/auth/crypto.py`) for the cross-file trace acceptance criterion**
`hash_password`'s PBKDF2 call was factored out into a new `src/auth/crypto.py::derive_key`, purely so the fixture has a genuine (not test-only-fabricated) chain spanning >=3 files to trace — SPEC.md's acceptance criterion. `tests/test_browse.py::test_get_file_slice_happy_path`'s hardcoded line numbers for `auth.py` shifted by one line as a result (`hash_password`'s `def` moved from line 17 to 18) and were updated accordingly. Verified live against a real model (not just `FakeLLMProvider`): asking to trace `create_user`'s password hashing produced a correctly-ordered, fully-cited four-file trace, matching the acceptance criterion's literal wording.

## Phase 2

**`symbols.id`/`endpoints.id`/`dependencies.id` follow `chunks.id`'s `AUTOINCREMENT` precedent (Phase 0)**
Same reasoning as Phase 0's `chunks.id` entry below: `index/graph_store.py` deletes-and-reinserts a file's `symbols`/`endpoints` rows (and a manifest's `dependencies` rows) on every reindex, and `symbol_refs.resolved_symbol_id` points at `symbols.id` by value — a reused rowid after a delete could silently point a ref at an unrelated symbol post-reindex. `symbols` uses `AUTOINCREMENT` for this reason; `endpoints`/`dependencies`/`symbol_refs`/`import_edges` aren't pointed at by id from anywhere else, so they keep the plain `INTEGER PRIMARY KEY` SPEC.md §4 specifies.

**Real bug: `parsing/symbols.py`'s docstring extraction returned `None` for every docstring — caught by a failing formal test, not by smoke-testing**
`_docstring()` assumed a definition's leading string-literal statement is always wrapped in an `expression_statement` node. True for many tree-sitter grammars, but the pinned tree-sitter-python grammar represents a bare string statement at the top of a block as a `string` node directly, with no `expression_statement` wrapper. Every earlier smoke-test of `symbols.py` (following this project's "verify AST structure → write code → smoke-test against a real/synthetic fixture" pattern) happened to check `is_exported`/`signature`, never a docstring's actual *content* — so this went unnoticed until `tests/test_symbols.py::test_python_class_and_methods` asserted `docstring == "Manages users."` and got `None` back. Fixed to accept either shape (`expression_statement` wrapping a `string`, or a bare `string` directly). The general lesson: smoke-testing that a field is merely *non-crashing* isn't the same as asserting its value is *correct* — only the latter caught this.

**Two more `parsing/symbols.py` bugs, found via targeted smoke-testing before any test file existed for it**
1. `_signature()` originally read from the decorator-inclusive `span_node`, so a `@dataclass`-decorated class's "signature" came out as `"@dataclass"` instead of `"class User:"`. Fixed to read from `inner_node` — the same "whole span including decorators" vs. "the definition itself" distinction Phase 1's chunker already draws via `unwrap_decorator`.
2. A method on an *exported* JS/TS class was reported `is_exported=False`, because only the class declaration itself is syntactically `export`-wrapped — its methods aren't. Fixed by threading a `container_exported` flag through the AST walk so a method inherits its enclosing container's exported-ness.
Both are now locked in by `tests/test_symbols.py` (written afterward, in this same phase, once the manual smoke-testing pattern had run its course).

**NestJS decorators are structurally different from Phase 1's chunker assumption — verified directly before writing the extractor, not assumed**
Phase 1's `chunker.py` found that a Python `@decorator`/JS `export` *wraps* its definition (`decorated_definition`/`export_statement` as a parent node). `parsing/extractors/endpoints/nestjs.py` needed the same answer for TS class/method decorators, and — per this project's now-standard "verify AST structure first" workflow — checking the actual tree-sitter output showed it's different: a *method*-level decorator is a preceding **sibling** of `method_definition` inside `class_body`, not a wrapper around it; a *class*-level decorator on an *exported* class is a sibling inside `export_statement`, not a child of `class_declaration`. Handled explicitly (`_class_decorators`/`_walk_class_body`) rather than reusing `chunker.py`'s `unwrap_decorator`, which is built for the wrapper shape only. No bug shipped here — flagged because the wrong assumption would have silently dropped every NestJS route had it not been checked first.

**Structured routes (`dependencies`/`endpoints`/`locate`) skip the cosmetic per-word streaming delay the LLM-backed routes use**
`generation/answer.py`'s token-replay pacing (`_TOKEN_REPLAY_DELAY_SECONDS`, from Phase 1) exists purely to make an already-complete LLM answer *feel* streamed to the UI. Measured against the `endpoints` route with all 9 of mini_repo's fixture endpoints, replaying at that pace pushed the SSE stream close to a full second end-to-end — for a repo with more endpoints than that, it would silently blow SPEC.md's "structured routes answer in <1s" acceptance criterion on cosmetic pacing alone, not any real work. Structured answers now stream with `pace=False`; measured latency dropped from ~850ms to sub-millisecond on the same fixture, confirmed via a direct timing script before locking it into `tests/test_answer_routes.py`'s `latency_ms < 1000` assertions.

**Query router's regex fast-path ordering, tuned against a 20-question labeled set (SPEC.md's own acceptance criterion)**
An early draft checked `endpoints`'s regex (`\b(endpoints?|routes?|...)\b`) before `explain`'s, so "Trace the request from route to database" (an `explain`-shaped question — "trace ... from X to Y") matched on the bare word "route" and misrouted to `endpoints`. Fixed by giving `explain`'s most unambiguous markers (`trace`, `walk me through`) top precedence ahead of every other route's regex, while leaving `explain`'s weaker markers (`how does`, `how is ... implemented`) checked last — those commonly co-occur with a more specific cue (e.g. "how does the dependency resolver work" should route to `dependencies`, not `explain`). Verified against `tests/test_router.py`'s 20-question labeled set (4 per route): 20/20 after the fix, versus 19/20 before it.

**Endpoint/dependency extraction scope decisions (each documented inline where implemented; cross-referenced here per the working agreement)**
- `express.py`/`rails.py` don't merge a mount-point prefix (`app.use("/api", router)`) or a Rails `namespace :api do ... end` block's prefix into the routes found inside — each route is read independently of its enclosing mount/namespace. Getting this right in general requires tracking which variable is mounted where (Express) or block-scope nesting (Rails); out of scope for the "≥90% of real endpoints" bar SPEC.md's acceptance criterion sets (mini_repo's Express fixture deliberately exercises this gap and still hits 100%), and documented as a known limitation in both modules' own docstrings.
- Go/Java/Rust/Ruby imports (`parsing/refs.py::extract_imports`) are always recorded as external/unresolved, never matched against `files`. Resolving them correctly needs classpath/crate/gem knowledge (Java's package-to-jar mapping, Cargo's dependency graph, Ruby's load path) this project doesn't model; no Phase 2 acceptance criterion depends on resolving them, so `import_edges.to_file_id` is NULL for these four languages by design, not by omission.
- `build.gradle`/`Gemfile` dependency parsing (`parsing/extractors/dependencies.py`) is regex-based against the common `dependencies { implementation '...' }` / `gem '...'` forms, not a full Groovy/Ruby parse — both are Turing-complete build DSLs, so a regex can only ever be "good enough for the common case," never provably correct for either. `package.json`/`pyproject.toml` — the two formats the acceptance criterion actually checks exact counts against — are parsed as real JSON/TOML instead, and matched exactly (4 and 5 dependencies respectively) against `tests/fixtures/mini_repo`'s manifests.

## Phase 1

**Answer generation buffers the full response (`LLMProvider.complete()`) instead of true token-by-token streaming, then replays it as chunked `token` SSE events**
Citation verification (`generation/citations.py`) needs the complete answer text before it can tell whether a claim's citations are valid — there's no way to verify a citation the model hasn't finished writing yet. That's fundamentally in tension with live streaming: either occasionally show the user an unverified (possibly-invalid-citation) draft as it's generated, or find another way to reconcile the two. Rather than invent new SSE event semantics beyond the frozen contract (SPEC.md §5) to support "clear the draft and restart" mid-stream, `generate_answer_events` calls `.complete()` (buffers), verifies, regenerates once if a claim was left unsupported, and only then emits `token` events by replaying the final text word-by-word with a small artificial delay. The user only ever sees the citation-checked answer; the cost is losing true first-token latency. `LLMProvider.stream()` is unused by this path as a result but stays in the protocol (SPEC.md §7.2 requires it) — Phase 3's agent loop is a more likely user of true streaming, where there's no equivalent verify-before-showing constraint.

**`chunks_fts` is a normal FTS5 table, not contentless (deviates from SPEC.md §4's `content=''`)**
Verified directly (not by inspection): a contentless FTS5 table can't be deleted from by rowid alone — `DELETE FROM chunks_fts WHERE rowid=?` raises `cannot DELETE from contentless fts5 table`. The only way to remove a row is FTS5's special command re-supplying the *exact original indexed values* (`INSERT INTO chunks_fts(chunks_fts, rowid, content, symbol_name, path) VALUES('delete', ?, ?, ?, ?)`), which since contentless tables store no text at all, means the caller has to track or re-fetch those values itself. `index/store.py::index_file` already deletes-and-reinserts a file's chunks whenever its content changes, so this would mean threading the *old* content/symbol_name/path through that path just to delete a lexical-index row. Switched to a regular FTS5 table (drops `content=''`) instead: `DELETE FROM chunks_fts WHERE rowid=?` just works, at the cost of one extra copy of each chunk's text living in FTS5's shadow tables — a storage micro-cost that doesn't matter at this project's scale, in exchange for real simplification of the chunk-replacement path.

**Chunker granularity: each function/method is its own chunk; each container gets a lightweight "shell" chunk, not a duplicate of its full body**
Not spelled out in SPEC.md's prose ("One chunk per function / method / class" is ambiguous on whether a class chunk should also contain its methods' text). Chose: every function/method/method-in-a-class becomes its own chunk (tagged `parent_symbol`), and every class/struct/interface/impl additionally gets one "shell" chunk — its signature plus whatever body content precedes its first nested method (docstring, attributes, fields) — rather than either (a) duplicating every method's text into a giant class-level chunk too, or (b) trying to reconstruct a class's "shell minus method bodies" by subtracting disjoint byte ranges (correct but fiddly; "everything before the first method" captures the common case — docstring/attributes before methods — without it). Module-level code not covered by any top-level definition (imports, constants, a trailing `if __name__ == "__main__":` block, *and any such code sitting between two definitions*) becomes its own "module" chunk per gap, not one chunk for the whole file — SPEC.md's "module-level code becomes one chunk" is read as "one chunk per contiguous stretch of it," since concatenating non-contiguous byte ranges across a file doesn't produce a chunk with a coherent, citable line range.

**Two real chunk-boundary bugs found by smoke-testing against real files, not by code review**
1. **Decorator/export wrappers caused overlapping chunks.** Python's `@decorator` puts the actual `class_definition`/`function_definition` one level down inside a `decorated_definition` node; JS/TS's `export`/`export default` does the same via `export_statement`. Not accounting for this, the *un*wrapped node's `start_byte` was used to compute where the preceding module/shell chunk should end — so a decorated/exported definition's own decorator line ended up included in **both** the preceding chunk and the definition's own chunk. Fixed with a generic `LanguageSpec.wrapper_types` + `_unwrap()` mechanism (only Python and JS/TS need it — verified TS decorators and Java annotations attach as a direct child of the definition node itself, already inside its span, no wrapper involved). Rust's `#[attribute]` is structurally different (a *preceding sibling*, not a wrapper) and isn't fixed the same way — left as a known small gap: the attribute line is neither duplicated nor included in any chunk.
2. **Module-level gaps *between* two definitions were silently dropped.** An earlier version only emitted a module chunk before the first top-level definition and after the last one; anything sitting between two definitions (a constant declared between two functions, a JS `export const foo = () => {...}` arrow-function export next to a `class`) fell into neither and was never chunked at all — real content loss, not just an unretrievable arrow function. Fixed by walking every gap between consecutive top-level definitions, not just the two end gaps.

Both were caught before being wired into the indexing pipeline, by chunking real fixture files and checking for overlapping/missing line ranges — not something a read-through of the code would have surfaced, since the logic looks locally correct at each individual call site.

## Phase 0

**`fastembed` (local ONNX embedding adapter) removed entirely; default embedding provider corrected to `voyage`**
SPEC.md §2 says two things: "default to a code-specialized model (`voyage-code-3`)" *and* "provide ... a local `fastembed` adapter for offline dev/tests." Both were implemented, but `config.py`/`.env.example` defaulted to `fastembed`, not `voyage` — my own choice, made for lower onboarding friction (no API key needed to try the system), never actually called for by the spec and never flagged as a deviation. That default made the system quietly ship with a general-purpose small English text model (`BAAI/bge-small-en-v1.5`) doing the retrieval-quality-critical embedding work instead of the code-specialized model the rest of the architecture assumes (§1's "core design bet" is specifically about embeddings understanding code) — a real quality regression hiding behind a convenience default. Once flagged, and given a real `VOYAGE_API_KEY` is available, the call was to remove `fastembed` rather than just fix the default: `EmbeddingProvider` still has two real adapters (`voyage`, `openai`) plus `FakeEmbeddingProvider` for tests, `embedding_provider` defaults to `voyage`, and `pyproject.toml`'s `[embeddings]` extra dropped `fastembed`/`onnxruntime` accordingly. This is a further deviation from SPEC.md §2's literal text (no local/offline/zero-key embedding path exists anymore) — worth knowing if a future contributor without any embedding API key needs to index something; re-adding a local adapter later is straightforward if that need resurfaces, ideally defaulted correctly this time.

**Tests were silently reading the developer's local `backend/.env` — fixed with `make_settings()` / `_env_file=None`**
`pydantic-settings` reads `env_file` (`backend/.env`) unconditionally on every `Settings()` construction unless told not to — including in tests, which mostly construct `Settings(data_dir=tmp_path / "data", ...)` directly rather than going through `get_settings()`. That meant a test asserting on a "default" value (e.g. `allow_local_repos is False`) was actually asserting on whatever happened to be in the developer's own gitignored `.env` at the time, not the documented class default in `config.py`. This had been true since Phase 0 but never surfaced as a failure, because nothing in `.env` disagreed with the compiled-in defaults — until `ALLOW_LOCAL_REPOS=true` was added there for local dev convenience, and `test_create_repo_rejects_local_path_by_default` immediately failed for the wrong reason (it read `true` from `.env`, not `False` from the default). Fixed by adding `tests/conftest.py::make_settings(tmp_path, **overrides)`, which passes `_env_file=None` — every test now goes through it instead of constructing `Settings(...)` directly. Verified by deliberately corrupting `backend/.env` with nonsense values and confirming the suite still passed unaffected.

**Local-path repos disabled by default at the API layer (`ALLOW_LOCAL_REPOS=false`)**
SPEC.md §1 lists "a local directory" as a first-class source alongside GitHub repos, and the capability is still fully intact — `ingest/source.py` is unchanged. But "local path" means local to wherever the *server* runs, not to whoever calls the API. For a hosted/multi-tenant deployment, accepting arbitrary filesystem paths from `POST /api/repos` is an information-disclosure hole (index `/etc`, a `.env` file, SSH keys — anything the server process can read). `api/repos.py::create_repo` now rejects `source` strings that classify as local unless `settings.allow_local_repos` is true; the flag defaults to `False` and is documented in `.env.example`. This only gates the public API — `source.py`, and every test that calls it directly, is untouched, and the test suite's own `Settings` instances set `allow_local_repos=True` explicitly (that's how the suite indexes `tests/fixtures/mini_repo` without a network call, per §7.2). For the single-user local dev setup this README targets, set `ALLOW_LOCAL_REPOS=true` in `backend/.env`.

**`uv` unavailable → pip + venv fallback**
The build machine doesn't have `uv` installed. SPEC.md §2 explicitly allows falling back to pip + venv, so `backend/` is set up as a standard venv + `pyproject.toml` (PEP 621, installed with `pip install -e .`). If `uv` becomes available later, `uv sync` should work unmodified against the same `pyproject.toml`.

**Python version, settled after three iterations: Homebrew's Python 3.12, `requires-python = ">=3.12"`**
This took three tries to get right, each one surfacing a real constraint:
1. Started on pyenv's 3.12.7, reasoning a brand-new interpreter would have worse compiled-wheel availability. Wrong axis: pyenv's own builds are compiled *without* `--enable-loadable-sqlite-extensions` by default, so `sqlite3.Connection.enable_load_extension` doesn't exist under it at all — fatal for `sqlite-vec`, which the whole architecture depends on (§2). (If you ever do want a pyenv interpreter here, build it with `PYTHON_CONFIGURE_OPTS="--enable-loadable-sqlite-extensions" pyenv install --force <version>` first.)
2. Switched to the system/Homebrew Python 3.14.6, which does support loadable extensions. That held up for `pyproject.toml`'s core dependencies — but the optional `[embeddings]` extra's `fastembed` (→ `onnxruntime`) had **no published wheel for 3.14 at all yet** (it's too new); `pip install -e ".[embeddings]"` failed outright.
3. Landed on Homebrew's Python 3.12.0 (`/usr/local/opt/python@3.12/bin/python3.12`, not pyenv's): verified directly to support loadable extensions (Homebrew's build flags differ from pyenv's), and every dependency installed cleanly. `requires-python` raised from `>=3.11` to `>=3.12` to match. `backend/.python-version` pins `3.12`.

The general lesson: verify loadable-extension support *and* compiled-wheel availability for the actual dependency set before picking an interpreter — neither alone is sufficient, and "newest available" is the wrong default for either axis on a project with compiled deps.

**Update after `fastembed` was later removed entirely** (see the entry above): step 2's *wheel*-availability failure (`onnxruntime` on 3.14) can no longer recur. But the 3.12 floor turned out to be necessary independent of `fastembed` anyway — `numpy` (required by `voyageai` itself, confirmed via `pip show numpy`) ships type stubs using PEP 695 (`type X = ...`) syntax that mypy can only parse when targeting 3.12+, regardless of what syntax our own code uses. So `requires-python = ">=3.12"` stays, now for a `voyageai`-driven reason rather than a `fastembed`-driven one — not leftover caution from a removed dependency.

**`chunk_vectors` dimension is parameterized per repo, not hardcoded to `FLOAT[1024]`**
SPEC.md §4 hardcodes the vec0 table to `FLOAT[1024]`, which matches `voyage-code-3` (the default). But the OpenAI adapter's default model is 1536-dim, and `FakeEmbeddingProvider` (tests) is 32-dim. Rather than force every provider to 1024 (padding/truncating vectors, which distorts cosine similarity), `db.py::get_repo_connection` creates `chunk_vectors` with whatever dimension the active `EmbeddingProvider.dim` reports, and refuses to reopen a repo DB with a provider of a different dimension (points you at reindexing instead of silently corrupting vectors).

**`chunks.id` uses `AUTOINCREMENT`, unlike the plain `INTEGER PRIMARY KEY` in SPEC.md §4**
Found via a failing test, not by inspection: a plain SQLite `INTEGER PRIMARY KEY` is a rowid alias and reuses deleted rowids. `index/store.py::index_file` deletes and reinserts a file's chunk rows whenever its content changes, so without `AUTOINCREMENT` a brand-new chunk could be assigned the same id as a chunk from an old version of the file. Current code already deletes the stale `chunk_vectors` row before that id gets reused, so there's no live correctness bug today — but a historical `query_log.chunk_ids_json` entry would silently start pointing at unrelated content after a later reindex, which is a bad failure mode for an audit trail. `AUTOINCREMENT` (via SQLite's `sqlite_sequence` bookkeeping) closes this off entirely for the cost of one keyword.

**Migrations only include what the current phase needs**
`db.py`'s `REPO_MIGRATIONS` v1 covers `files`, `chunks`, and `query_log` — the tables Phase 0 tasks actually populate. `chunks_fts`, `symbols`, `symbol_refs`, `import_edges`, `dependencies`, `endpoints`, and `summaries` from SPEC.md §4 will land as migration v2/v3/... in the phases that introduce them, keeping schema growth traceable to the phase that needed it.

**Phase 0 chunker is intentionally naive**
Per SPEC.md §6 Phase 0 task 4: fixed ~1500-char windows with 200-char overlap, no AST awareness. This is deliberately replaced in Phase 1 by `parsing/chunker.py` (tree-sitter). Not a deviation — flagging so it's not mistaken for the final chunking strategy.

**Frontend renders plaintext answers in Phase 0 — no `react-markdown`/syntax highlighting yet, and those deps aren't installed**
SPEC.md §6 Phase 0 task 9 explicitly scopes the frontend to "chat panel, plaintext answers"; citation chips + `CodeViewer` click-through are named Phase 1 tasks. `react-markdown`, `rehype-highlight`, and `highlight.js` (listed in §2's tech stack for the *eventual* system) were installed and then removed again once it was clear nothing in Phase 0 would use them — installed-but-inert dependencies are a worse starting point than adding them back in Phase 1 when `MessageBubble`/`CodeViewer` actually need them. The `citations`/`sources` SSE events are still consumed and shown (as plain non-interactive text), since dropping visible signal the backend already sends would be a worse UX than the code cost of rendering it plainly.

**`api/browse.py` and `api/evaluate.py` not stubbed in Phase 0**
SPEC.md §3's full repo layout lists these upfront, but they belong to Phase 1 (`GET /file` for the citation click-through) and Phase 4 (eval) respectively. Per the working agreement ("work one phase at a time"), only `api/repos.py` and `api/query.py` — the endpoints Phase 0 tasks actually require — were built, to avoid dead code.

**FastAPI dependency footgun: `Depends(fn)` where `fn`'s own params aren't themselves `Depends(...)`-wrapped**
`db.py` originally exposed `iter_registry_connection(settings: Settings | None = None)` for use as `Depends(iter_registry_connection)`. This silently breaks dependency overrides: because `settings` wasn't itself declared as `Depends(get_settings)`, FastAPI doesn't know to resolve it through the DI system at all — on `api/query.py` it triggered request-body validation errors (FastAPI tried to parse a `Settings` sub-model out of the JSON body), and on `api/repos.py` it silently fell back to the real global `get_settings()`, so tests were writing to their temp DB but reading from the real `data/dbs/_registry.db`. Fixed by deleting the shared helper and defining `registry_connection_dependency(settings: Settings = Depends(get_settings))` locally in each API module (matching the pattern already used for `embedding_provider_dependency`/`llm_provider_dependency` in `query.py`). Lesson encoded as a comment at both call sites.

**README's install command must match whatever `.env.example`'s default `EMBEDDING_PROVIDER` needs**
Found from a real run (back when the default was `fastembed`): the README's setup command was `pip install -e ".[dev]"`, but the default provider's package lived behind the optional `[embeddings]` extra — a fresh setup following the README hit `ModuleNotFoundError` the first time it actually tried to index a repo. `README.md` installs `.[dev,embeddings]` now. The general point stands even after `fastembed`'s removal (see above): whatever `EMBEDDING_PROVIDER` defaults to, the default install command must actually provide it.

**No live embedding/LLM keys available in this environment**
No `ANTHROPIC_API_KEY` / `VOYAGE_API_KEY` in the shell. All backend tests use `FakeEmbeddingProvider` / a fake LLM provider and make zero network calls (required by acceptance criteria). Live end-to-end indexing against a real GitHub repo requires the user to supply real keys in `backend/.env`.

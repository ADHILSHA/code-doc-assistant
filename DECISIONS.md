# Decisions log

Deviations from SPEC.md, with rationale. Newest first.

---

## Phase 2

**`symbols.id`/`endpoints.id`/`dependencies.id` follow `chunks.id`'s `AUTOINCREMENT` precedent (Phase 0)**
Same reasoning as Phase 0's `chunks.id` entry below: `index/graph_store.py` deletes-and-reinserts a file's `symbols`/`endpoints` rows (and a manifest's `dependencies` rows) on every reindex, and `symbol_refs.resolved_symbol_id` points at `symbols.id` by value — a reused rowid after a delete could silently point a ref at an unrelated symbol post-reindex. `symbols` uses `AUTOINCREMENT` for this reason; `endpoints`/`dependencies`/`symbol_refs`/`import_edges` aren't pointed at by id from anywhere else, so they keep the plain `INTEGER PRIMARY KEY` SPEC.md §4 specifies.

**Real bug: `parsing/symbols.py`'s docstring extraction returned `None` for every docstring — caught by a failing formal test, not by smoke-testing**
`_docstring()` assumed a definition's leading string-literal statement is always wrapped in an `expression_statement` node. True for many tree-sitter grammars, but the pinned tree-sitter-python grammar represents a bare string statement at the top of a block as a `string` node directly, with no `expression_statement` wrapper. Every earlier smoke-test of `symbols.py` (following this project's "verify AST structure → write code → smoke-test against a real/synthetic fixture" pattern) happened to check `is_exported`/`signature`, never a docstring's actual *content* — so this went unnoticed until `tests/test_symbols.py::test_python_class_and_methods` asserted `docstring == "Manages users."` and got `None` back. Fixed to accept either shape (`expression_statement` wrapping a `string`, or a bare `string` directly). The general lesson: smoke-testing that a field is merely *non-crashing* isn't the same as asserting its value is *correct* — only the latter caught this.

**Two more `parsing/symbols.py` bugs, found via targeted smoke-testing before any test file existed for it**
1. `_signature()` originally read from the decorator-inclusive `span_node`, so a `@dataclass`-decorated class's "signature" came out as `"@dataclass"` instead of `"class User:"`. Fixed to read from `inner_node` — the same "whole span including decorators" vs. "the definition itself" distinction Phase 1's chunker already draws via `unwrap_decorator`.
2. A method on an *exported* JS/TS class was reported `is_exported=False`, because only the class declaration itself is syntactically `export`-wrapped — its methods aren't. Fixed by threading a `container_exported` flag through the AST walk so a method inherits its enclosing container's exported-ness.
Both are now locked in by `tests/test_symbols.py` (written afterward, in this same phase, once the manual smoke-testing pattern had run its course).

**NestJS decorators are structurally different from Phase 1's chunker assumption — verified directly before writing the extractor, not assumed**
Phase 1's `chunker.py` found that a Python `@decorator`/JS `export` *wraps* its definition (`decorated_definition`/`export_statement` as a parent node). `parsing/extractors/endpoints/nestjs.py` needed the same answer for TS class/method decorators, and — per this project's now-standard "verify AST structure first" workflow — checking the actual tree-sitter output showed it's different: a *method*-level decorator is a preceding **sibling** of `method_definition` inside `class_body`, not a wrapper around it; a *class*-level decorator on an *exported* class is a sibling inside `export_statement`, not a child of `class_declaration`. Handled explicitly (`_class_decorators`/`_walk_class_body`) rather than reusing `chunker.py`'s `unwrap_decorator`, which is built for the wrapper shape only. No bug shipped here — flagged because the wrong assumption would have silently dropped every NestJS route had it not been checked first.

**Structured routes (`dependencies`/`endpoints`/`locate`) skip the cosmetic per-word streaming delay the LLM-backed routes use**
`generation/answer.py`'s token-replay pacing (`_TOKEN_REPLAY_DELAY_SECONDS`, from Phase 1) exists purely to make an already-complete LLM answer *feel* streamed to the UI. Measured against the `endpoints` route with all 9 of mini_repo's fixture endpoints, replaying at that pace pushed the SSE stream close to a full second end-to-end — for a repo with more endpoints than that, it would silently blow SPEC.md's "structured routes answer in <1s" acceptance criterion on cosmetic pacing alone, not any real work. Structured answers now stream with `pace=False`; measured latency dropped from ~850ms to sub-millisecond on the same fixture, confirmed via a direct timing script before locking it into `tests/test_answer_routes.py`'s `latency_ms < 1000` assertions.

**Query router's regex fast-path ordering, tuned against a 20-question labeled set (SPEC.md's own acceptance criterion)**
An early draft checked `endpoints`'s regex (`\b(endpoints?|routes?|...)\b`) before `explain`'s, so "Trace the request from route to database" (an `explain`-shaped question — "trace ... from X to Y") matched on the bare word "route" and misrouted to `endpoints`. Fixed by giving `explain`'s most unambiguous markers (`trace`, `walk me through`) top precedence ahead of every other route's regex, while leaving `explain`'s weaker markers (`how does`, `how is ... implemented`) checked last — those commonly co-occur with a more specific cue (e.g. "how does the dependency resolver work" should route to `dependencies`, not `explain`). Verified against `tests/test_router.py`'s 20-question labeled set (4 per route): 20/20 after the fix, versus 19/20 before it.

**Endpoint/dependency extraction scope decisions (each documented inline where implemented; cross-referenced here per the working agreement)**
- `express.py`/`rails.py` don't merge a mount-point prefix (`app.use("/api", router)`) or a Rails `namespace :api do ... end` block's prefix into the routes found inside — each route is read independently of its enclosing mount/namespace. Getting this right in general requires tracking which variable is mounted where (Express) or block-scope nesting (Rails); out of scope for the "≥90% of real endpoints" bar SPEC.md's acceptance criterion sets (mini_repo's Express fixture deliberately exercises this gap and still hits 100%), and documented as a known limitation in both modules' own docstrings.
- Go/Java/Rust/Ruby imports (`parsing/refs.py::extract_imports`) are always recorded as external/unresolved, never matched against `files`. Resolving them correctly needs classpath/crate/gem knowledge (Java's package-to-jar mapping, Cargo's dependency graph, Ruby's load path) this project doesn't model; no Phase 2 acceptance criterion depends on resolving them, so `import_edges.to_file_id` is NULL for these four languages by design, not by omission.
- `build.gradle`/`Gemfile` dependency parsing (`parsing/extractors/dependencies.py`) is regex-based against the common `dependencies { implementation '...' }` / `gem '...'` forms, not a full Groovy/Ruby parse — both are Turing-complete build DSLs, so a regex can only ever be "good enough for the common case," never provably correct for either. `package.json`/`pyproject.toml` — the two formats the acceptance criterion actually checks exact counts against — are parsed as real JSON/TOML instead, and matched exactly (4 and 5 dependencies respectively) against `tests/fixtures/mini_repo`'s manifests.

## Phase 1

**Answer generation buffers the full response (`LLMProvider.complete()`) instead of true token-by-token streaming, then replays it as chunked `token` SSE events**
Citation verification (`generation/citations.py`) needs the complete answer text before it can tell whether a claim's citations are valid — there's no way to verify a citation the model hasn't finished writing yet. That's fundamentally in tension with live streaming: either occasionally show the user an unverified (possibly-invalid-citation) draft as it's generated, or find another way to reconcile the two. Rather than invent new SSE event semantics beyond the frozen contract (SPEC.md §5) to support "clear the draft and restart" mid-stream, `generate_answer_events` calls `.complete()` (buffers), verifies, regenerates once if a claim was left unsupported, and only then emits `token` events by replaying the final text word-by-word with a small artificial delay. The user only ever sees the citation-checked answer; the cost is losing true first-token latency. `LLMProvider.stream()` is unused by this path as a result but stays in the protocol (SPEC.md §7.2 requires it) — Phase 3's agent loop is a more likely user of true streaming, where there's no equivalent verify-before-showing constraint.

**`chunks_fts` is a normal FTS5 table, not contentless (deviates from SPEC.md §4's `content=''`)**
Verified directly (not by inspection): a contentless FTS5 table can't be deleted from by rowid alone — `DELETE FROM chunks_fts WHERE rowid=?` raises `cannot DELETE from contentless fts5 table`. The only way to remove a row is FTS5's special command re-supplying the *exact original indexed values* (`INSERT INTO chunks_fts(chunks_fts, rowid, content, symbol_name, path) VALUES('delete', ?, ?, ?, ?)`), which since contentless tables store no text at all, means the caller has to track or re-fetch those values itself. `index/store.py::index_file` already deletes-and-reinserts a file's chunks whenever its content changes, so this would mean threading the *old* content/symbol_name/path through that path just to delete a lexical-index row. Switched to a regular FTS5 table (drops `content=''`) instead: `DELETE FROM chunks_fts WHERE rowid=?` just works, at the cost of one extra copy of each chunk's text living in FTS5's shadow tables — a storage micro-cost that doesn't matter at this project's scale, in exchange for real simplification of the chunk-replacement path.

**Chunker granularity: each function/method is its own chunk; each container gets a lightweight "shell" chunk, not a duplicate of its full body**
Not spelled out in SPEC.md's prose ("One chunk per function / method / class" is ambiguous on whether a class chunk should also contain its methods' text). Chose: every function/method/method-in-a-class becomes its own chunk (tagged `parent_symbol`), and every class/struct/interface/impl additionally gets one "shell" chunk — its signature plus whatever body content precedes its first nested method (docstring, attributes, fields) — rather than either (a) duplicating every method's text into a giant class-level chunk too, or (b) trying to reconstruct a class's "shell minus method bodies" by subtracting disjoint byte ranges (correct but fiddly; "everything before the first method" captures the common case — docstring/attributes before methods — without it). Module-level code not covered by any top-level definition (imports, constants, a trailing `if __name__ == "__main__":` block, *and any such code sitting between two definitions*) becomes its own "module" chunk per gap, not one chunk for the whole file — SPEC.md's "module-level code becomes one chunk" is read as "one chunk per contiguous stretch of it," since concatenating non-contiguous byte ranges across a file doesn't produce a chunk with a coherent, citable line range.

**Two real chunk-boundary bugs found by smoke-testing against real files, not by code review**
1. **Decorator/export wrappers caused overlapping chunks.** Python's `@decorator` puts the actual `class_definition`/`function_definition` one level down inside a `decorated_definition` node; JS/TS's `export`/`export default` does the same via `export_statement`. Not accounting for this, the *un*wrapped node's `start_byte` was used to compute where the preceding module/shell chunk should end — so a decorated/exported definition's own decorator line ended up included in **both** the preceding chunk and the definition's own chunk. Fixed with a generic `LanguageSpec.wrapper_types` + `_unwrap()` mechanism (only Python and JS/TS need it — verified TS decorators and Java annotations attach as a direct child of the definition node itself, already inside its span, no wrapper involved). Rust's `#[attribute]` is structurally different (a *preceding sibling*, not a wrapper) and isn't fixed the same way — left as a known small gap: the attribute line is neither duplicated nor included in any chunk.
2. **Module-level gaps *between* two definitions were silently dropped.** An earlier version only emitted a module chunk before the first top-level definition and after the last one; anything sitting between two definitions (a constant declared between two functions, a JS `export const foo = () => {...}` arrow-function export next to a `class`) fell into neither and was never chunked at all — real content loss, not just an unretrievable arrow function. Fixed by walking every gap between consecutive top-level definitions, not just the two end gaps.

Both were caught before being wired into the indexing pipeline, by chunking real fixture files and checking for overlapping/missing line ranges — not something a read-through of the code would have surfaced, since the logic looks locally correct at each individual call site.

## Phase 0

**`fastembed` (local ONNX embedding adapter) removed entirely; default embedding provider corrected to `voyage`**
SPEC.md §2 says two things: "default to a code-specialized model (`voyage-code-3`)" *and* "provide ... a local `fastembed` adapter for offline dev/tests." Both were implemented, but `config.py`/`.env.example` defaulted to `fastembed`, not `voyage` — my own choice, made for lower onboarding friction (no API key needed to try the system), never actually called for by the spec and never flagged as a deviation. That default made the system quietly ship with a general-purpose small English text model (`BAAI/bge-small-en-v1.5`) doing the retrieval-quality-critical embedding work instead of the code-specialized model the rest of the architecture assumes (§1's "core design bet" is specifically about embeddings understanding code) — a real quality regression hiding behind a convenience default. Once flagged, and given a real `VOYAGE_API_KEY` is available, the call was to remove `fastembed` rather than just fix the default: `EmbeddingProvider` still has two real adapters (`voyage`, `openai`) plus `FakeEmbeddingProvider` for tests, `embedding_provider` defaults to `voyage`, and `pyproject.toml`'s `[embeddings]` extra dropped `fastembed`/`onnxruntime` accordingly. This is a further deviation from SPEC.md §2's literal text (no local/offline/zero-key embedding path exists anymore) — worth knowing if a future contributor without any embedding API key needs to index something; re-adding a local adapter later is straightforward if that need resurfaces, ideally defaulted correctly this time.

**Tests were silently reading the developer's local `backend/.env` — fixed with `make_settings()` / `_env_file=None`**
`pydantic-settings` reads `env_file` (`backend/.env`) unconditionally on every `Settings()` construction unless told not to — including in tests, which mostly construct `Settings(data_dir=tmp_path / "data", ...)` directly rather than going through `get_settings()`. That meant a test asserting on a "default" value (e.g. `allow_local_repos is False`) was actually asserting on whatever happened to be in the developer's own gitignored `.env` at the time, not the documented class default in `config.py`. This had been true since Phase 0 but never surfaced as a failure, because nothing in `.env` disagreed with the compiled-in defaults — until `ALLOW_LOCAL_REPOS=true` was added there for local dev convenience, and `test_create_repo_rejects_local_path_by_default` immediately failed for the wrong reason (it read `true` from `.env`, not `False` from the default). Fixed by adding `tests/conftest.py::make_settings(tmp_path, **overrides)`, which passes `_env_file=None` — every test now goes through it instead of constructing `Settings(...)` directly. Verified by deliberately corrupting `backend/.env` with nonsense values and confirming the suite still passed unaffected.

**Local-path repos disabled by default at the API layer (`ALLOW_LOCAL_REPOS=false`)**
SPEC.md §1 lists "a local directory" as a first-class source alongside GitHub repos, and the capability is still fully intact — `ingest/source.py` is unchanged. But "local path" means local to wherever the *server* runs, not to whoever calls the API. For a hosted/multi-tenant deployment, accepting arbitrary filesystem paths from `POST /api/repos` is an information-disclosure hole (index `/etc`, a `.env` file, SSH keys — anything the server process can read). `api/repos.py::create_repo` now rejects `source` strings that classify as local unless `settings.allow_local_repos` is true; the flag defaults to `False` and is documented in `.env.example`. This only gates the public API — `source.py`, and every test that calls it directly, is untouched, and the test suite's own `Settings` instances set `allow_local_repos=True` explicitly (that's how the suite indexes `tests/fixtures/mini_repo` without a network call, per §7.2). For the single-user local dev setup this README targets, set `ALLOW_LOCAL_REPOS=true` in `backend/.env`.

**`uv` unavailable → pip + venv fallback**
The build machine doesn't have `uv` installed. SPEC.md §2 explicitly allows falling back to pip + venv, so `backend/` is set up as a standard venv + `pyproject.toml` (PEP 621, installed with `pip install -e .`). If `uv` becomes available later, `uv sync` should work unmodified against the same `pyproject.toml`.

**Python version, settled after three iterations: Homebrew's Python 3.12, `requires-python = ">=3.12"`**
This took three tries to get right, each one surfacing a real constraint:
1. Started on pyenv's 3.12.7, reasoning a brand-new interpreter would have worse compiled-wheel availability. Wrong axis: pyenv's own builds are compiled *without* `--enable-loadable-sqlite-extensions` by default, so `sqlite3.Connection.enable_load_extension` doesn't exist under it at all — fatal for `sqlite-vec`, which the whole architecture depends on (§2). (If you ever do want a pyenv interpreter here, build it with `PYTHON_CONFIGURE_OPTS="--enable-loadable-sqlite-extensions" pyenv install --force <version>` first.)
2. Switched to the system/Homebrew Python 3.14.6, which does support loadable extensions. That held up for `pyproject.toml`'s core dependencies — but the optional `[embeddings]` extra's `fastembed` (→ `onnxruntime`) had **no published wheel for 3.14 at all yet** (it's too new); `pip install -e ".[embeddings]"` failed outright.
3. Landed on Homebrew's Python 3.12.0 (`/usr/local/opt/python@3.12/bin/python3.12`, not pyenv's): verified directly to support loadable extensions (Homebrew's build flags differ from pyenv's), and every dependency installed cleanly. `requires-python` raised from `>=3.11` to `>=3.12` to match. `backend/.python-version` pins `3.12`.

The general lesson: verify loadable-extension support *and* compiled-wheel availability for the actual dependency set before picking an interpreter — neither alone is sufficient, and "newest available" is the wrong default for either axis on a project with compiled deps.

**Update after `fastembed` was later removed entirely** (see the entry above): step 2's *wheel*-availability failure (`onnxruntime` on 3.14) can no longer recur. But the 3.12 floor turned out to be necessary independent of `fastembed` anyway — `numpy` (required by `voyageai` itself, confirmed via `pip show numpy`) ships type stubs using PEP 695 (`type X = ...`) syntax that mypy can only parse when targeting 3.12+, regardless of what syntax our own code uses. So `requires-python = ">=3.12"` stays, now for a `voyageai`-driven reason rather than a `fastembed`-driven one — not leftover caution from a removed dependency.

**`chunk_vectors` dimension is parameterized per repo, not hardcoded to `FLOAT[1024]`**
SPEC.md §4 hardcodes the vec0 table to `FLOAT[1024]`, which matches `voyage-code-3` (the default). But the OpenAI adapter's default model is 1536-dim, and `FakeEmbeddingProvider` (tests) is 32-dim. Rather than force every provider to 1024 (padding/truncating vectors, which distorts cosine similarity), `db.py::get_repo_connection` creates `chunk_vectors` with whatever dimension the active `EmbeddingProvider.dim` reports, and refuses to reopen a repo DB with a provider of a different dimension (points you at reindexing instead of silently corrupting vectors).

**`chunks.id` uses `AUTOINCREMENT`, unlike the plain `INTEGER PRIMARY KEY` in SPEC.md §4**
Found via a failing test, not by inspection: a plain SQLite `INTEGER PRIMARY KEY` is a rowid alias and reuses deleted rowids. `index/store.py::index_file` deletes and reinserts a file's chunk rows whenever its content changes, so without `AUTOINCREMENT` a brand-new chunk could be assigned the same id as a chunk from an old version of the file. Current code already deletes the stale `chunk_vectors` row before that id gets reused, so there's no live correctness bug today — but a historical `query_log.chunk_ids_json` entry would silently start pointing at unrelated content after a later reindex, which is a bad failure mode for an audit trail. `AUTOINCREMENT` (via SQLite's `sqlite_sequence` bookkeeping) closes this off entirely for the cost of one keyword.

**Migrations only include what the current phase needs**
`db.py`'s `REPO_MIGRATIONS` v1 covers `files`, `chunks`, and `query_log` — the tables Phase 0 tasks actually populate. `chunks_fts`, `symbols`, `symbol_refs`, `import_edges`, `dependencies`, `endpoints`, and `summaries` from SPEC.md §4 will land as migration v2/v3/... in the phases that introduce them, keeping schema growth traceable to the phase that needed it.

**Phase 0 chunker is intentionally naive**
Per SPEC.md §6 Phase 0 task 4: fixed ~1500-char windows with 200-char overlap, no AST awareness. This is deliberately replaced in Phase 1 by `parsing/chunker.py` (tree-sitter). Not a deviation — flagging so it's not mistaken for the final chunking strategy.

**Frontend renders plaintext answers in Phase 0 — no `react-markdown`/syntax highlighting yet, and those deps aren't installed**
SPEC.md §6 Phase 0 task 9 explicitly scopes the frontend to "chat panel, plaintext answers"; citation chips + `CodeViewer` click-through are named Phase 1 tasks. `react-markdown`, `rehype-highlight`, and `highlight.js` (listed in §2's tech stack for the *eventual* system) were installed and then removed again once it was clear nothing in Phase 0 would use them — installed-but-inert dependencies are a worse starting point than adding them back in Phase 1 when `MessageBubble`/`CodeViewer` actually need them. The `citations`/`sources` SSE events are still consumed and shown (as plain non-interactive text), since dropping visible signal the backend already sends would be a worse UX than the code cost of rendering it plainly.

**`api/browse.py` and `api/evaluate.py` not stubbed in Phase 0**
SPEC.md §3's full repo layout lists these upfront, but they belong to Phase 1 (`GET /file` for the citation click-through) and Phase 4 (eval) respectively. Per the working agreement ("work one phase at a time"), only `api/repos.py` and `api/query.py` — the endpoints Phase 0 tasks actually require — were built, to avoid dead code.

**FastAPI dependency footgun: `Depends(fn)` where `fn`'s own params aren't themselves `Depends(...)`-wrapped**
`db.py` originally exposed `iter_registry_connection(settings: Settings | None = None)` for use as `Depends(iter_registry_connection)`. This silently breaks dependency overrides: because `settings` wasn't itself declared as `Depends(get_settings)`, FastAPI doesn't know to resolve it through the DI system at all — on `api/query.py` it triggered request-body validation errors (FastAPI tried to parse a `Settings` sub-model out of the JSON body), and on `api/repos.py` it silently fell back to the real global `get_settings()`, so tests were writing to their temp DB but reading from the real `data/dbs/_registry.db`. Fixed by deleting the shared helper and defining `registry_connection_dependency(settings: Settings = Depends(get_settings))` locally in each API module (matching the pattern already used for `embedding_provider_dependency`/`llm_provider_dependency` in `query.py`). Lesson encoded as a comment at both call sites.

**README's install command must match whatever `.env.example`'s default `EMBEDDING_PROVIDER` needs**
Found from a real run (back when the default was `fastembed`): the README's setup command was `pip install -e ".[dev]"`, but the default provider's package lived behind the optional `[embeddings]` extra — a fresh setup following the README hit `ModuleNotFoundError` the first time it actually tried to index a repo. `README.md` installs `.[dev,embeddings]` now. The general point stands even after `fastembed`'s removal (see above): whatever `EMBEDDING_PROVIDER` defaults to, the default install command must actually provide it.

**No live embedding/LLM keys available in this environment**
No `ANTHROPIC_API_KEY` / `VOYAGE_API_KEY` in the shell. All backend tests use `FakeEmbeddingProvider` / a fake LLM provider and make zero network calls (required by acceptance criteria). Live end-to-end indexing against a real GitHub repo requires the user to supply real keys in `backend/.env`.
